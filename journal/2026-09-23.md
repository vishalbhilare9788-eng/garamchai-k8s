# Session 2 (same day): Incident — cluster state lost after a host hang

## What happened
- The Windows laptop hung (resource crunch) some time after 15:17 UTC. All 3 VMs died without a clean shutdown (`last -x` shows `crash`).
- After the restart (15:34–15:37), `kubectl` returned **403 Forbidden** for `kubernetes-admin`, both from cka-m and from Windows.

## Investigation (evidence, not guesses)
| Evidence | Meaning |
|---|---|
| `kubectl auth whoami` → groups `kubeadm:cluster-admins`; binding `kubeadm:cluster-admins` NotFound | 403 = authentication OK, RBAC denied. Since kubeadm 1.29, admin.conf relies on this binding (not `system:masters`) |
| Every ClusterRole/Binding, kube-system Role, and namespaces `default`/`kube-system` created at 15:36 today | The API server re-created its bootstrap objects on an almost empty etcd |
| Only 4 static pods left; no calico-node, CoreDNS, kube-proxy; no CRDs; cka-m lost its control-plane label/taint | All non-bootstrap state gone. Nodes cka-m and w1 re-registered; cka-w2's Node object (16d) randomly survived |
| `kube-system` cannot be deleted through the API (NamespaceLifecycle) | Rules out a human `kubectl delete`: data vanished underneath the API server |
| etcd log: `backend-size-in-use 25 kB`, and `consistentIndex 80323` > WAL `commit-index 80308` | The DB was ahead of the WAL, which is impossible if fsync'd writes are durable. Acknowledged writes were lost when the host hung |
| etcd log: `opened backend db took 2.8s`; VM disks live on **E: = HDD** | Slow storage for etcd |

**Root cause:** the host hung and the VMs were hard-powered-off. Writes that etcd believed were saved were lost (host/VMware write caching on an HDD), leaving etcd internally inconsistent. Single etcd member + no etcd backup = total loss of cluster state.

**Contributing factor:** host memory. 16 GB RAM, 3 VMs × 4 GB. Commit charge 14.7 / 18.1 GB with only the VMs + Task Manager running, so VS Code + a browser can push it over the limit.

## Mistakes & lessons
| Mistake | By | Lesson |
|---|---|---|
| First hypothesis blamed the Argo CD cleanup ("a delete removed the binding") | Claude | One missing object ≠ a targeted delete. Check creation timestamps of *everything* before naming a cause |
| No etcd backup existed | Both | Back up etcd from day 1, and copy snapshots **off** the node |
| VMs not shut down before heavy host use | Vishal | `sudo poweroff` (w2 → w1 → m) before closing VMware or loading the host |

## Decision
Rebuild the cluster (`kubeadm reset` + `init` from a versioned `kubeadm-config.yaml`) instead of repairing an etcd store in an unknown state. Nothing of GaramChai was deployed yet. Add scheduled etcd snapshots in Phase 0.
