1. The cast: master and worker components

The analogy used throughout: GaramChai as a chain of chai shops.

  • The master (control plane) is the head office. It never makes chai itself. It decides, records and supervises.
  • The workers are the branches with kitchens, where the chai (your containers) is actually made.

In our lab, cka-m is the head office, and cka-w1 and cka-w2 are the branches. The head office also has a small kitchen (kubelet + CRI-O), but a sign on the door, the taint node-role.kubernetes.io/control-plane:NoSchedule, says "no customer orders here".

2. Tools vs components

People mix these up in interviews. A component is part of the running cluster; a tool is something you run to talk to it.

ToolTalks toUsed forAnalogy
kubectlthe API server, over the network, from anywhereEveryday work: get, apply, describe, logsCalling the front counter
crictlCRI-O on this one node (local socket)Debugging when the API server is down: crictl ps, crictl logsWalking into the kitchen and looking at the stove yourself
kubeadmthe node itselfBuilding the cluster: init, join, upgrade, resetThe construction company

kubectl vs crictl kubectl shows what Kubernetes thinks is running. crictl shows what is actually running on that node. When the API server is dead, kubectl is blind and crictl still works. That's why we used crictl ps during the etcd restore drill while the control plane was stopped.

3. One order, followed through every component

You run kubectl create deployment chai --image=nginx --replicas=2. Here's what happens, in order:

  1. kubectl sends the Deployment to the API server.
  2. The API server checks your certificate and RBAC permissions, then saves the Deployment in etcd.
  3. The Deployment controller (inside controller-manager) notices it and creates a ReplicaSet.
  4. The ReplicaSet controller notices "wants 2, has 0" and creates 2 Pod objects with no node yet.
  5. The scheduler picks cka-w1 and cka-w2 and writes that down.
  6. The kubelet on cka-w1 notices "a pod is assigned to me".
  7. It asks CRI-O to pull and start the container, and CRI-O calls Calico for a pod IP.
  8. The kubelet reports "Running"; the API server saves it in etcd. kubectl get pods shows Running.
The two ideas that explain everything
  1. Nobody talks to anybody directly. Everything goes through the API server.
  2. Every component just watches and reacts. There's no boss giving orders. If a pod dies, step 4 simply notices "wants 2, has 1" again. That's what "self-healing" means.

4. How the cluster boots: the 4 layers

The puzzle: the API server runs inside a pod. But pods are normally created through the API server. So how does the first pod ever start?

The answer: static pods. The kubelet reads YAML files from /etc/kubernetes/manifests/ and starts them directly from disk, without asking the API server.

Why restarts after a boot are normal The 4 static pods start at the same time. The API server crashes and retries until etcd answers; the controller-manager and scheduler retry until the API server answers. So a few restarts right after a boot are harmless. Always check when a restart happened before worrying.
Interview line "The kubelet is a systemd service. It starts the control plane as static pods from /etc/kubernetes/manifests, which solves the chicken-and-egg problem, because the API server itself runs in a pod. Once the API server is up, the DaemonSets bring up the network, nodes turn Ready, and normal workloads get scheduled. When a cluster won't come up, I debug from the bottom: systemctl status kubelet → crictl ps -a → crictl logs of the API server → etcd."

6. How a worker joins safely (TLS bootstrap)

A new worker has nothing: no certificate, no kubeconfig, just the join command. The question is how two strangers learn to trust each other.

StepWhat happensOffice analogy
1. DiscoveryThe worker reads cluster-info (in kube-public). The token proves it came from the real cluster; the CA cert hash in the join command pins the CA, so a fake API server can't pretendCompare the office's stamp with the fingerprint you were given
2. TLS bootstrapThe kubelet logs in with the token and sends a CSR: "please sign a certificate for system:node:cka-w1"Use a visitor pass to apply for an employee badge
3. ApprovalThe CSR is auto-approved and signed by the cluster CAHR stamps the badge
4. Real credentialsThe kubelet saves its certificate; the token is no longer neededVisitor pass returned
5. RegistrationThe kubelet creates its Node object (InternalIP = --node-ip)Name on the office board
6. HeartbeatEvery ~10 s it renews its Lease in kube-node-lease; missing heartbeats → NotReady"I'm alive" check-ins
7. DaemonSetskube-proxy and calico-node are created on the new node automaticallyNew branch gets phones and roads
Why workers don't get admin.conf A worker's kubelet can only see its own node and pods (the Node authorizer). If an admin kubeconfig sat on a worker, one container escape would give an attacker the whole cluster.

7. Why nodes are NotReady until the CNI is installed

  1. Right after kubeadm init, there's no network config in /etc/cni/net.d/, so the kubelet reports NetworkReady=false and the Node is NotReady.
  2. The node lifecycle controller adds the taint node.kubernetes.io/not-ready:NoSchedule.
  3. CoreDNS stays Pending. In our lab it tolerated not-ready only with effect NoExecute, not NoSchedule. A toleration must match both the key and the effect.
  4. We install Calico: its DaemonSet copies the CNI binary and config onto each node, gives the node a /26 block of pod IPs, and shares routes over BGP.
  5. The config file exists → NetworkReady → node Ready → taint removed → CoreDNS gets scheduled.
Linux analogyThe machine has booted, but the network service hasn't started yet, so nothing that needs the network can come up.

9. Namespaced vs cluster-scoped objects

The common confusion (we had it too) "kube-system is cluster scope, garamchai is application scope" is wrong. Both are just namespaces, the same kind of thing. Scope is a property of the object type (the kind:), not of a namespace.
  • Namespaced kind: every object of this type must live inside some namespace (kube-system, garamchai, default…).
  • Cluster-scoped kind: objects of this type live outside all namespaces. There's no namespace: field at all.

The apartment-building analogy

  • Namespaces = apartments. kube-system is the caretaker's flat; garamchai is ours. Both are ordinary apartments.
  • Namespaced objects = furniture. A sofa is always inside some apartment. Two apartments can each have a sofa called "sofa" without any conflict.
  • Cluster-scoped objects = the building itself: floors, lifts, the list of apartments. They don't belong to one flat, because every flat uses them.
Namespaced (belongs to one app/team)Cluster-scoped (shared by everyone)
Pod, Deployment, ReplicaSet, StatefulSet, DaemonSetNode
Service, ConfigMap, Secret, ServiceAccountNamespace (a flat can't be inside itself)
PersistentVolumeClaim (the app's request for storage)PersistentVolume (the actual storage), StorageClass
Role, RoleBindingClusterRole, ClusterRoleBinding, CustomResourceDefinition, IngressClass

Test to use: "Can two teams each have their own one with the same name?" If yes, it's namespaced. Rule of thumb: if the kind's name starts with "Cluster", it's cluster-scoped.

Why is a Node cluster-scoped? It's shared infrastructure: cka-w1 runs pods from every namespace at the same time, so it can't belong to any one of them.

kubectl api-resources --namespaced=true    # list namespaced kinds
kubectl api-resources --namespaced=false   # list cluster-scoped kinds
kubectl get nodes -n kube-system           # -n is ignored: nodes have no namespace
Real lesson from Phase 0 Deleting the argocd namespace did not delete Argo CD's 3 CRDs and 6 ClusterRoles/Bindings, because they're cluster-scoped. We had to delete them separately.

10. Capacity vs Allocatable, and taints you never added

10.1 Capacity vs Allocatable (per node)

Allocatable = Capacity − kube-reserved − system-reserved − eviction threshold

Our worker:  ~3.8 GiB capacity − (no reservations set) − 200 Mi eviction threshold
           ≈ 3.58 GiB allocatable
  • Capacity: everything the node has.
  • Allocatable: what's left for pods after keeping some back for the OS, the kubelet and a safety margin.
  • The scheduler uses Allocatable, and adds up the pods' requests, not their actual usage. A node can be 90% idle and still reject a pod, because the requests are "full".
kubectl get node cka-w1 -o jsonpath='{.status.capacity.memory}{"  "}{.status.allocatable.memory}{"\n"}'

10.2 The disk-pressure taint on cka-w2 (from our audit)

A three-step chain, and interviewers want all three steps:

  1. kubelet saw free disk fall below its eviction threshold → set the node condition DiskPressure=True → evicted a pod to free space.
  2. kube-controller-manager (node lifecycle controller) turned the condition into the taint node.kubernetes.io/disk-pressure:NoSchedule.
  3. kube-scheduler respected the taint and stopped placing pods on cka-w2, so everything crowded onto cka-w1.

It disappeared on its own after we added a 40 GB disk: the condition went False (after a ~5-minute wait so it doesn't flap), and the taint was removed.

Don't remove condition taints by handKubernetes owns them and puts them straight back. Fix the cause (the disk), and the taint goes by itself.

Not kube-proxy: kube-proxy only programs Service rules and has nothing to do with disks or taints.

11.2 Humans vs programs

The analogy: the API server is a security guard at an office entrance. Humans and delivery robots come through the door, and the guard treats them differently.

Humans (you, an intern)Programs (order-service, backup Job)
IdentityA name inside a certificate (CN= = name, O= = group), or a company login (OIDC)A ServiceAccount object
Stored in the cluster?No. There's no User object. kubectl get users failsYes, in etcd: kubectl get serviceaccounts
How it's checkedThe guard checks the card has the CA's seal, then believes the name and group printed on itA token mounted into the pod
WhyHumans already have an identity elsewhere (HR, AD, SSO)Programs only exist inside the cluster
# See your own ID card (on cka-m):
sudo grep client-certificate-data /etc/kubernetes/admin.conf | awk '{print $2}' | base64 -d \
  | openssl x509 -noout -subject -issuer -enddate
# subject = O = kubeadm:cluster-admins, CN = kubernetes-admin   ← group + name
# issuer  = CN = kubernetes                                     ← the cluster CA's seal

So your group comes from the O= field of the client certificate inside admin.conf; the file is only the wallet.

11.3 Why the CA key is dangerous

  • Whoever holds ca.key can print any ID card, for example CN=hacker, O=kubeadm:cluster-admins, and the guard lets them in as admin.
  • Kubernetes can't revoke client certificates. A stolen admin certificate works until it expires (up to 1 year with kubeadm). A stolen password, by contrast, can be changed or disabled in seconds.
  • That's why the PKI backup is root-only, admin.conf is never shared or committed, and companies log humans in through OIDC (single sign-on) instead.

Answer key

  1. c) kube-apiserver. Everything else goes through it.
  2. kubelet and CRI-O. Something has to exist before any pod can run: the kubelet starts pods, and CRI-O actually runs their containers.
  3. The kubelet on cka-w1 notices the assignment and asks CRI-O to pull the image and start it (Calico gives it an IP).
  4. b) crictl. It talks to CRI-O on that node directly.
  5. Pods defined by files in /etc/kubernetes/manifests/ that the kubelet runs without the API server. They solve the chicken-and-egg problem: the API server runs in a pod, but pods are normally created through the API server.
  6. Usually not. All control-plane pods start at once, and the API server retries until etcd is ready. Check when the restarts happened (did the count grow after boot?) before worrying.
  7. No CNI yet: the kubelet reports NetworkReady=false, so the node is NotReady and gets the not-ready:NoSchedule taint; CoreDNS doesn't tolerate that effect. Installing Calico fixes it.
  8. It's baked into certificates and kubeconfigs and is hard to change after init. A name or VIP can later point at a load balancer in front of several masters (HA); a node IP ties the cluster to one machine.
  9. A fake API server: the new node verifies that the cluster's CA matches the hash it was given, so it won't trust an impostor.
  10. Namespaced: Pod, Service, Secret, Deployment, ConfigMap, Role, PersistentVolumeClaim. Cluster-scoped: Node, Namespace, PersistentVolume, ClusterRole, StorageClass.
  11. It's shared infrastructure: it runs pods from every namespace at the same time, so it can't belong to any one of them.
  12. Cluster-scoped ones: CRDs, ClusterRoles, ClusterRoleBindings (and PVs). Deleting a namespace only deletes objects inside it. It happened with Argo CD.
  13. Allocatable = capacity minus kube-reserved, system-reserved and the eviction threshold (200 Mi for us), plus memory the kernel keeps. The scheduler uses Allocatable.
  14. The scheduler adds up requests, not real usage. If existing pods requested most of Allocatable, the node is "full" for scheduling even though it's idle.
  15. kubelet saw low disk → set DiskPressure=True and evicted a pod → node lifecycle controller (controller-manager) added the taint → scheduler avoided the node. After the disk was grown, the condition cleared and the taint was removed automatically.
  16. 401 = authentication failed ("who are you?"). 403 = authenticated but not authorised by RBAC ("you may not").
  17. From the O= (organisation) field of the client certificate inside admin.conf. The CN is the user name.
  18. Client certificates can't be revoked in Kubernetes; it stays valid until expiry (up to 1 year). A password can be changed or disabled in seconds, and often has a second factor.
  19. Humans are managed outside the cluster (certificates signed by the CA, or OIDC); Kubernetes just trusts the name and groups it's given. Programs live inside the cluster, so Kubernetes manages their identities itself.
  20. kubeadm:cluster-admins. It's created by kubeadm, not part of the API server's bootstrap RBAC, so the API server doesn't reconcile it; only the built-in ClusterRoles/Bindings come back automatically.
