The four networks, why they must never overlap, how a packet really travels,
what we fixed (ADR-003), CoreDNS, and how to design K8s networking in production
Why this matters Networking is the hardest thing to change after a cluster exists. The Pod CIDR, Service CIDR, CNI and node addressing are effectively permanent; changing them usually means rebuilding the cluster. That's why interviewers love networking questions.

2.1 Why they must never overlap

Linux decides where to send a packet by looking up the destination in its routing table. If two networks share addresses, the lookup can pick the wrong one.

Before our fix:  ens34 = 10.0.0.x/8   →  "10.0.0.0 to 10.255.255.255 is on ens34"
                 Service range 10.96.0.0/16 is INSIDE that  →  overlap
After:           ens34 = 10.0.0.x/24  →  only 10.0.0.0 – 10.0.0.255   →  no overlap

It happened to work before, because kube-proxy rewrites Service IPs before packets leave, but any hiccup would have sent packets down the wrong interface. That's the worst kind of bug to debug.

Two more overlaps to remember
  • 172.17.0.0/16 is our Pod CIDR and Docker's default bridge. So never install Docker on the nodes. We build images on Windows (Docker Desktop) instead.
  • MetalLB IPs must be below 192.168.64.128, because VMware's DHCP hands out .128–.254.

4. Follow the packet: 6 journeys

① kubectl on Windows → API server

Windows ──(network 1)──► 192.168.64.128:6443 on cka-m ──► kube-apiserver
kubeconfig uses the name k8s-api, which Windows resolves to 192.168.64.128 (hosts file)

② Worker → API server (kubelet reporting "I'm alive")

cka-w1 10.0.0.1 ──(network 2)──► k8s-api = 10.0.0.100:6443     static on both ends: DHCP can't break it

③ Pod on w1 → pod on w2 (IPIP: an envelope inside an envelope)

How does cka-w1 know that 172.17.62.128/26 lives on cka-w2? Calico's BGP agent (BIRD) shares routes between nodes:

172.17.62.128/26 via 10.0.0.2 dev tunl0 proto bird
172.17.95.128/26 via 10.0.0.1 dev tunl0 proto bird

④ Pod → Service IP (e.g. DNS at 10.96.0.10)

pod ──► dst 10.96.0.10:53
        iptables rules (written by kube-proxy on EVERY node) rewrite the destination:
        10.96.0.10 → one of the CoreDNS pods        ← this is DNAT
    ──► then travels like journey ③

No machine owns 10.96.0.10. It's a rule, not an interface. So you can't ping a Service IP (ICMP isn't covered by the rules), but you can connect to its port.

⑤ Pod → internet

pod ──► node rewrites the source to its own IP (SNAT / masquerade) ──► ens33 ──► VMware NAT ──► internet

⑥ Browser → GaramChai (Phase 7, not built yet)

browser ──► https://garamchai.test (hosts file → a MetalLB IP such as 192.168.64.50)
        ──► MetalLB answers ARP "that IP is at cka-w1's MAC" ──► Traefik ──► app pods
Lab gotcha: ping doesn't work inside pods CRI-O's default capabilities exclude NET_RAW, which ping needs, so ping fails with "permission denied" (containerd's defaults include it). Test with TCP instead: wget, nc, curl.

5.1 Split-horizon name resolution for k8s-api

The same name resolves to a different address depending on who asks:

Who asksFilek8s-api resolves toWhy
The nodes/etc/hosts10.0.0.100Cluster traffic stays on the static network
WindowsC:\Windows\System32\drivers\etc\hosts192.168.64.128The only network Windows can reach

Because kubeadm puts k8s-api into the API server's certificate, the TLS check passes from both sides. No certificate hacks, no insecure-skip-tls-verify.

Interview line "In my lab the nodes had two NICs, and each Kubernetes component was picking a different one. I pinned everything (API server advertise address, kubelet node-ip, Calico autodetection) to a static /24, which also removed an overlap between a /8 node network and the Service CIDR. The API endpoint is a DNS name with split-horizon resolution, so the cluster doesn't depend on DHCP."

6. CoreDNS: the cluster's phone directory

Pods get a new IP every time they restart, so apps never use pod IPs. They use names, and CoreDNS turns a name into the Service's stable IP.

kubectl -n kube-system get deployment coredns   # 2 replicas
kubectl -n kube-system get svc kube-dns         # 10.96.0.10: still called kube-dns, a historical name
kubectl -n kube-system get configmap coredns -o yaml   # its config, the "Corefile"

The kubelet writes every pod's /etc/resolv.conf:

nameserver 10.96.0.10
search garamchai.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

google.comForwarded to the node's upstream DNScalling an external API
Two DNS gotchas we hit or should know
  • busybox nslookup: versions after 1.28 ignore the search line, so nslookup kubernetes.default returns NXDOMAIN even when DNS is fine. Use the FQDN, or busybox:1.28.
  • ndots:5: names with fewer than 5 dots try the search suffixes first, so google.com causes 3–4 wasted lookups. Fixes: trailing dot (google.com.), dnsConfig per pod, or NodeLocal DNSCache.

6.1 "A pod can't resolve names": the checklist

  1. Are the CoreDNS pods running? kubectl -n kube-system get pods -l k8s-app=kube-dns
  2. Does the kube-dns Service have endpoints? (get endpointslices)
  3. From a test pod, look up the FQDN.
  4. Check /etc/resolv.conf inside the failing pod.
  5. Read the CoreDNS logs.
  6. Is a NetworkPolicy blocking UDP/TCP 53? (We'll meet this in Phase 8.)

Also check MTU (overlays add headers: IPIP 20 bytes, VXLAN 50; a mismatch gives "small requests work, big ones hang") and firewall ports: 6443 API, 2379–2380 etcd, 10250 kubelet, 30000–32767 NodePort, 179/TCP BGP, IP protocol 4 for IPIP, 4789/UDP VXLAN.

60-second interview answer "I start with the IP plan, because it's the one thing you can't change later: node, pod and service ranges that don't overlap with each other or anything the cluster connects to. Then the CNI: an overlay like Calico or Cilium on-prem, or the cloud CNI on EKS/AKS with subnets sized for pod IPs. Then HA: nodes across zones and a load-balanced API endpoint. Then traffic in (load balancer + Ingress or Gateway with TLS) and out (NAT with fixed egress IPs). Then DNS, then security: private subnets, security groups, default-deny NetworkPolicies, a private API endpoint. In my lab I found and fixed a /8 node network overlapping the Service CIDR and node IPs on DHCP."

Answer key

  1. LAN/NAT 192.168.64.0/24 (ens33), cluster 10.0.0.0/24 (ens34), Pods 172.17.0.0/16, Services 10.96.0.0/16. Pods are virtual (Calico overlay); Services are purely virtual (only iptables rules).
  2. /8 covered 10.0.0.0–10.255.255.255, which includes the Service range 10.96.0.0/16. Overlapping ranges can route packets down the wrong interface. It only worked because kube-proxy rewrites Service IPs first.
  3. Docker's default bridge uses 172.17.0.0/16, the same as our Pod CIDR, which would break pod routing.
  4. VMware's DHCP hands out .128–.254; a MetalLB IP inside that pool could be given to another machine too.
  5. The pod's packet (inner: 172.17.95.130 → 172.17.62.131) is wrapped in a node packet (outer: 10.0.0.1 → 10.0.0.2), sent over the cluster network, and unwrapped on the other node.
  6. Calico's BGP agent (BIRD) shares each node's /26 block, which appears as a route: 172.17.62.128/26 via 10.0.0.2 dev tunl0 proto bird.
  7. No interface owns a ClusterIP; only iptables/IPVS rules for its TCP/UDP ports exist. ICMP isn't translated.
  8. Nothing at connection time. It has already written iptables rules on every node; the kernel DNATs 10.96.0.10 to one of the CoreDNS pod IPs.
  9. The same name resolves differently depending on who asks. Nodes: k8s-api → 10.0.0.100 (hosts file); Windows: → 192.168.64.128. Both match the certificate, because k8s-api is in it.
  10. API server advertiseAddress (10.0.0.100), kubelet --node-ip, and Calico IP_AUTODETECTION_METHOD=cidr=10.0.0.0/24.
  11. Not necessarily. CRI-O drops the NET_RAW capability that ping needs. Test with TCP (wget, nc, curl).
  12. The Service in front of the CoreDNS pods (10.96.0.10). The name is historical, from before CoreDNS replaced kube-dns, and kept for compatibility.
  13. busybox nslookup (after 1.28) ignores the search domains, so it looked up the literal name. DNS itself was fine.
  14. Names with fewer than 5 dots try the search suffixes first, so external names cause several wasted lookups. That multiplies DNS load. Fix with a trailing dot, dnsConfig, or NodeLocal DNSCache.
  15. CoreDNS pods running → kube-dns endpoints exist → FQDN lookup from a test pod → the pod's resolv.conf → CoreDNS logs → NetworkPolicy blocking port 53.
  16. Running out of IP addresses, because every pod takes a real VPC IP. Size subnets properly, use prefix delegation or a secondary CIDR.
  17. Node/VPC subnets, Pod CIDR, Service CIDR, and every network the cluster will connect to: corporate LAN, VPNs, peered VPCs, other clusters, on-prem data centres.
  18. An MTU mismatch: the overlay header makes large packets too big, and they get dropped.
