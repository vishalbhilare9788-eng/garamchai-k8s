1. Why audit before building

An architect never deploys onto infrastructure they haven't inspected. Before writing one YAML we need the facts: which version? what's running? how much capacity is really there? which restrictions (taints) exist?

The first lesson came immediately The plan assumed 2 GB workers. The audit measured 4 GB. And it found a problem nobody had mentioned: disk. Always trust measured data over what anyone remembers, including yourself.

3. Fixing the disk and cleaning up

3.1 Why the disks were small

The Ubuntu installer with LVM gives the root volume only about half the disk by default and leaves the rest unused. We added a 40 GB disk (sdb) to each VM and joined it to the volume group.

LVM in plain words: physical disks (PV) are poured into one big pool (VG); from the pool you cut logical volumes (LV) that the filesystem sits on. Adding a disk means making it a PV, adding it to the pool, and growing the LV.

sudo pvcreate /dev/sdb                                   # 1. make the new disk an LVM physical volume
sudo vgextend ubuntu-vg /dev/sdb                         # 2. add it to the pool
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv   # 3. grow the volume; -r also grows the filesystem, online
df -h /

Result: 58–67 GB per node at ~13 % used. cka-w2's disk-pressure taint cleared by itself, because Kubernetes owns condition taints.

3.2 Cleanup, and a scope lesson

Deleting the argocd namespace left 3 CRDs and 6 ClusterRoles/Bindings behind. They're cluster-scoped, so they don't live in any namespace. We deleted them separately.

4. The incident: 403 Forbidden for the admin

  • The Windows laptop ran out of resources and hung. All three VMs died without a clean shutdown (last -x showed crash).
  • After the restart, kubectl returned 403 Forbidden for kubernetes-admin, both from cka-m and from Windows.

5. The investigation: evidence, not guesses

A mistake in the investigation, recorded honestly The first hypothesis blamed the Argo CD cleanup ("a delete must have removed the binding"). That was wrong. One missing object is not the same as a targeted delete. Checking the creation timestamps of everything showed the real picture: the whole store had been reset.

6. Root cause and contributing factors

Root cause The host hung, the VMs were hard-powered-off, and writes that etcd believed were saved were lost (host/VMware write caching on an HDD). etcd was left internally inconsistent. One etcd member + no backup = total loss of cluster state.

Contributing factors

  • Host memory: 16 GB laptop, 3 VMs × 4 GB. Commit charge 14.7 of 18.1 GB with only the VMs running, so VS Code and a browser could push it over the edge.
  • No etcd backup existed.
  • VMs weren't shut down before heavy use of the host.

What we changed

ChangeWhy
Windows page file 8–16 GB on the SSD (commit limit now ~24 GB)More headroom before the host hangs
VMware "fit all VM memory into reserved host RAM", 12 GB reservedVMs don't get swapped out by the host
cka-m reduced to 3 GBLess memory pressure on the host
Clean shutdown order w2 → w1 → m before heavy host useNo more hard power-offs
Automated etcd backups + restore drill (study notes 4)Next time, restore instead of rebuild

Interesting finding afterwards: the WAL fsync average was 1.5 ms on an HDD, which is "too good". Most likely VMware acknowledges fsync from its write cache before the data reaches the disk. That's fast, and it's exactly why acknowledged writes were lost in the crash. We kept the disks and got protection from off-node backups and clean shutdowns instead.

7. How to tell this story in an interview (STAR)

PartWhat to say
Situation"In my kubeadm lab, the host hung and all VMs were powered off hard. Afterwards the admin got 403 on every request."
Task"Find out why, restore a working cluster, and make sure it can't happen the same way again."
Action"whoami showed authentication was fine, so it was RBAC. The kubeadm:cluster-admins binding was missing. My first guess, an accidental delete, was wrong: creation timestamps showed every built-in object had just been re-created, and the etcd log showed the DB index ahead of the WAL, meaning acknowledged writes were lost. With one etcd member and no backup, repair wasn't trustworthy, so I rebuilt from a versioned kubeadm config."
Result"The cluster came back identical, from Git. I added automated etcd snapshots with a systemd timer, copies off the node, and a tested restore drill, plus host memory fixes and a shutdown procedure."

8. The rebuild: a cluster defined in Git

We rebuilt instead of repairing, because an etcd store in an unknown state produces bugs you can never explain. Nothing of GaramChai was deployed yet, so nothing was lost that mattered.

8.1 What kubeadm reset keeps and wipes

SurvivesWiped
OS, CRI-O, kubeadm/kubelet/kubectl packages, cached images, /etc/default/kubelet/etc/kubernetes (certs, kubeconfigs, manifests), /var/lib/etcd, kubelet state

Not cleaned by reset, so we did it ourselves: /etc/cni/net.d, /var/lib/calico, iptables rules, ~/.kube. Then a reboot, for a clean slate.

8.3 Validation saved us twice

  1. The old config (from Sep 6) had a duplicate key (serializeImagePulls) that kubeadm 1.35 rejects in strict mode. A rebuild with it would have failed half-way through init.
  2. The new config started with --- after the header comments, which creates an empty first document ("kind and apiVersion is mandatory"). --- goes only between documents.
HabitValidate (kubeadm config validate, kubectl apply --dry-run=server) before anything destructive.

Answer key

  1. Workers had 4 GB, not 2 GB; disk (not RAM) was the real problem; the runtime was CRI-O, not containerd.
  2. PVs (disks) are poured into a VG (the pool); LVs are cut from the pool and carry the filesystem. pvcreate /dev/sdb, vgextend ubuntu-vg /dev/sdb, lvextend -r -l +100%FREE ….
  3. It's a condition taint owned by Kubernetes: once free disk rose above the threshold, the kubelet cleared DiskPressure and the controller removed the taint.
  4. Cluster-scoped objects (CRDs, ClusterRoles, ClusterRoleBindings): they're not inside any namespace, so a namespace delete doesn't touch them.
  5. Authentication works; authorization (RBAC) fails. Look for the missing Role/Binding.
  6. kube-system itself had been re-created, and it can't be deleted through the API, so the data vanished underneath the API server.
  7. The database was ahead of its write-ahead log: writes that had been acknowledged as durable weren't actually on disk. Storage lost data.
  8. It explained one missing object with a targeted delete. Lesson: check creation timestamps of everything before naming a cause.
  9. A hard power-off lost writes etcd believed were durable, leaving a single-member etcd inconsistent, and there was no backup to restore.
  10. An etcd store in an unknown state produces unexplainable bugs, nothing important was deployed, and a versioned config made the rebuild repeatable.
  11. /etc/cni/net.d, /var/lib/calico, iptables rules, users' ~/.kube.
  12. A duplicate serializeImagePulls key in the old config; a leading --- creating an empty first document.
  13. A stable name (not a node IP) that can later point at a load balancer for HA; it's baked into certs and kubeconfigs and hard to change after init.
  14. An HDD can't really persist in 1.5 ms; the host was acknowledging from its write cache, which is exactly how "saved" writes were lost in the crash.
  15. See section 7: host hang → admin 403; whoami showed RBAC; timestamps + etcd index proved storage loss; rebuilt from Git and added tested backups and host fixes.
